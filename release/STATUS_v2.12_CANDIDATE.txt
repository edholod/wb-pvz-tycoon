ХРАНЕНИЕ И СИНХРОНИЗАЦИЯ
Существующий Telegram initData проверяется HMAC на Edge Function. Облако загружается до запуска движка. Все операции идут через прежний writer/revision CAS; ошибки замораживают запись, конфликты возвращают 409. Перенос активного устройства защищён owner guard. Новые поля вложены в существующие ключи.
Новый lossless codec упаковывает goodsLedger блоками по 128 в gzip: локально UTF16, в HTTP base64. Никакие товары/истории не удаляются. Длина и checksum проверяются. Старое plain и candidate LZ декодируются. Все клиенты должны загружать cloud-sync.js?v=2.12 до движка. Если packed save открыт старым клиентом, API возвращает 426 вместо повреждения данных. Не откатывать один frontend к версии без codec!

ЧТО НЕЛЬЗЯ ЛОМАТЬ
- 10 разрешённых top-level ключей облачного payload. Новые поля вложены в s.work212 и ty173Data.work212, приватность в прежнем ключе priv47.
- Никаких reset/save-key rename/очистки localStorage ради миграции.
- s — активная ветка; pvz34 — сеть; деньги общие, state веток нельзя складывать как отдельные стартовые балансы.
- Telegram HMAC: исключать только hash, учитывать signature; user ID брать только из проверенного initData. Не отключать проверку ради дебага.
- writer UUID + revision CAS/409, owner-transfer guard, freeze при облачной ошибке, previous_payload.
- Имеющееся оборудование, старые уровни >3, история отзывов, коллекции, награды/бонусы/задачи/ветки сохраняются.
- Новые награды фиксируются до анимации, анимация не управляет экономикой.
- Обновления модуля только через исходники + build-release.py; не добавлять повторно патчи v2.10/v2.11.
- Токен бота/service_role/подписи Telegram не выводить и не класть в файлы/репозиторий. Browser publishable key в исходнике публичный, не service secret.
- Известный прежний риск импорта .pizda поверх облачного состояния НЕ исправлялся этой задачей: локальный импорт с reload может проиграть облачному сохранению. Нужна отдельная атомарная cloud-import процедура. Не рекомендовать как гарантированный перенос поверх существующего облака.

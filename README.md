# WB PVZ TYCOON — прототип экономики

- `economy.json`: базовые настройки экономики, склада, отзывов и персонала.
- `equipment.json`: игровой каталог оборудования и уровни улучшений.
- `engine.py`: рабочая Python-модель покупки, улучшения, износа, ремонта и эффектов оборудования.
- `test_engine.py`: 6 автоматических проверок.

Запуск: `python engine.py`.
Проверка: `python -m unittest -v test_engine.py`.

Это серверный прототип, **не Telegram Mini App**. Для релиза ещё нужны интерфейс, авторизация Telegram, база данных, обработка заказов и синхронизация времени. Все суммы и эффекты вымышлены для игрового баланса, а не официальные правила WB.

## Логистика v1.3
`logistics.py` — отдельные товары, приёмка, хранение, выдача, возвраты, поиск, расследования и подтверждённые списания. Риск ошибок растёт при переполнении; помощник и стеллажи уменьшают риск. Используйте `python -m unittest discover -v` для проверки. Это модель игрового прототипа: пока нет автоматического потока заказов, почасового планировщика, Telegram или базы данных.

## Автоматическая симуляция v1.4
`simulation.py` — ускоренные игровые дни: поставки, выдачи, возвраты, оборот, игровые вознаграждения, аренда, смены, замены, помощник, расходники, отзывы и рейтинг. `test_simulation.py` — проверки повторяемости, денег, склада и событий.

Пример:
```python
from engine import new_game
from simulation import simulate_days
state = new_game()
reports = simulate_days(state, 7)
print(reports[-1])
```

**Ограничения:** это пока офлайн-прототип Python, не сервер Telegram. Процент 5%, сезонные коэффициенты, стоимость смен и частота отзывов — условные игровые параметры, не официальные тарифы WB. В модели нет реального календаря, реальной статистики WB, онлайн-сохранений и авторизации. Одна смена обрабатывается за день, отзывы появляются в пределах игровых часов 9–21. Для реальной работы Mini App нужен серверный планировщик и база данных.

## Персонал v1.5
`staff.py` — отдельные сотрудники, графики 2/2 и 5/2, найм, увольнение, обучение, усталость, мораль, невыходы (включая связанные с алкоголем), срочная замена и учёт задержанной зарплаты. `simulation.py` теперь берёт состав смены и навыки из кадрового модуля; старое поле `operations.staff` сохранено только для совместимости и не управляет сменой. `test_staff.py` проверяет ключевые сценарии.

**Пока не реализовано:** полноценные трудовые договоры, налоги с ФОТ, начисление задолженности по зарплате из ежедневных смен, заявления на увольнение, конфликты между сотрудниками, управление заменой вручную и интерфейс. Причины невыхода — вымышленные игровые события, а не выводы о реальных людях. Не предназначено для расчёта настоящей зарплаты.

## Происшествия v1.6
`incidents.py` — 12 шаблонов происшествий (клиенты, сотрудники, поставки, склад, оборудование, электричество), очередь решений и репутация. `simulate_day` создаёт 1–2 происшествия в день; решение игрок принимает через `resolve_incident(state, incident_id, option_id)`. Расходы возникают только после выбора, нехватка денег проверяется, повторное решение запрещено. 32 теста прошли. Пока нет интерфейса, автозакрытия событий, сотен уникальных сюжетов или интеграции с Telegram. Репутация происшествий пока отдельно от рейтинга отзывов.

## Браузерный интерфейс v1.7
Откройте `web/index.html` в браузере. Это отдельная интерактивная демоверсия на JavaScript с локальным сохранением через localStorage. Есть открытие ПВЗ, дни, склад, оборудование, помощник, отзывы, происшествия, финансовая история. **Это не подключение Python-движка**: баланс и игровые формулы демонстрационные и не синхронизированы с Python-модулями. Нет Telegram-авторизации, серверной базы данных и фоновой симуляции. Для реального многопользовательского релиза необходимо перенести расчёты на сервер, верифицировать Telegram initData и хранить состояние в БД.

## v1.15 — адрес и уникальный номер ПВЗ
При открытии ПВЗ вводится адрес (6–200 символов), присваивается случайный 64-битный идентификатор вида PVZ-XXXXXXXXXXXXXXXХ, данные сохраняются в локальном состоянии браузера и показываются на главной. Адрес экранируется при выводе. Это локальный прототип: гарантированная глобальная уникальность и синхронизация между аккаунтами потребуют серверной БД с UNIQUE-ограничением.
